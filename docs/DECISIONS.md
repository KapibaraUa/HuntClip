Допущения и решения, принятые без вопросов к владельцу (правило: выбирать простейший вариант).

## Фаза 0

1. **Корень репозитория** это корень рабочей папки (`automatization/`), а не вложенная `cliphunter/` из раздела 5 плана. Структура внутри та же.
2. **Окружение.** Python 3.12 и зависимости ставятся в локальный `.venv` через `uv` (по просьбе владельца: ничего не ставить на машину). FFmpeg и Docker уже были в системе, я их не ставил. yt-dlp запускается как `python -m yt_dlp` из venv.
3. **Interactions API вместо generateContent.** Актуальная документация (2026-10-20) даёт все примеры для `gemini-3.8-flash` через `client.interactions.create`. Имена параметров взяты из документации, см. `docs/CALIBRATION.md`, раздел 0.
4. **Модель.** `gemini-3.8-flash` без дополнительной проверки по просьбе владельца. Имя встречается в документации, расхождений не замечено.
5. **Калибровка не запускалась.** У владельца пока нет стрима и эталонных моментов, а тратить деньги на калибровку нельзя. `scripts/calibrate.py` по умолчанию ничего не отправляет (dry run, только оценка стоимости). Платный режим включается флагом `--live`, ограничен `CALIBRATION_MAX_COST_USD` (по умолчанию 1 USD), без ключа отказывается работать. `docs/CALIBRATION.md` содержит сверку документации и пометки «не измерено».
6. **Значения-заглушки до калибровки:** `URL_OFFSETS_OK=false` (безопасный вариант: file-mode), `URL_TS_RELATIVE_TO_WINDOW=true`, `MEDIA_RES_SCAN=low`, `MEDIA_RES_REFINE=high`, `THINKING_LEVEL=medium` (умолчание модели). Это не результат измерений.
7. **«Обычное разрешение»** из плана трактуется как `high` (по документации около 300 токенов/с). Для проверки `medium` и `unspecified` нужен отдельный прогон.
8. **Числа, которых нет в плане**, выбраны как рабочие: `CLIP_MIN_S=20`, `CLIP_MAX_S=90`, `CLIP_TOLERANCE_S=5`, `MAX_CANDIDATES_PER_HOUR=20`, `MAX_PER_30MIN=6`, `MAX_COST_USD_PER_JOB=5`, `CONFIRM_ABOVE_USD=1`, `RETENTION_DAYS=14`.
9. **Параметры сверх раздела 12**, нужные для расчётов: `THINKING_LEVEL`, `CLIP_TOLERANCE_S`, `TOKENS_PER_SEC_LOW/HIGH`, `CONTEXT_TOKENS`, `CONTEXT_SHARE_MAX`, `CALIBRATION_MAX_COST_USD`, `LOG_LEVEL`. Все в конфиге.
10. **Цены.** Из страницы pricing (Standard): 0.75 и 3.75 USD за 1M до 2026-12-31, с 2027-01-01 это 1.50 и 7.50. В конфиге стоят вводные, их надо поменять в январе.
11. **Учёт токенов.** Мышление тарифицируется как выход (по документации). Токены tool-use в агентном режиме я считаю входными: в документации сказано только, что это отдельная категория. Это допущение, его надо проверить по счёту при первом агентном прогоне.
12. **Журнал `api_calls`** в фазе 0 пишется в `data/logs/api_calls.jsonl` (БД и миграции относятся к фазе 3). Поля те же, что в таблице раздела 6.
13. **Кэш** хранится в `data/cache/llm/{sha256}.json` (ключ: модель, видео-часть запроса, промпт, системная инструкция, схема, уровень мышления, версия промпта).
14. **Подготовка куска для калибровки:** yt-dlp скачивает только нужную секцию (до 720p) с `--force-keyframes-at-cuts`, FFmpeg делает прокси по разделу 9 плана. Это не «лучший формат» из S1, но для Gemini разницы нет (прокси всё равно 720p).
15. **Пункт 2 калибровки (относительно чего таймкоды)** проверяется без второго платного вызова: ответ url+offsets разбирается дважды (как относительный к окну и как абсолютный), побеждает гипотеза с большим числом совпадений с эталоном при IoU не ниже 0,5.
16. **Пункт 1 калибровки, «без offsets».** Запуск на всём видео делается, только если оно не длиннее `url_full_max_duration_s` (900 с по умолчанию). Иначе пропускается с пометкой: на длинном видео это дорого. Флаг `URL_OFFSETS_OK` решается по отношению фактических входных токенов к ожидаемым (`длина окна × токенов/с`), порог 1.5.
17. **Пункт 7 (точность таймкодов)**: средняя абсолютная ошибка начала и конца на парах «эталон и найденный клип» с IoU не ниже 0,5 (владелец не задал метрику).
18. **Пункт 4 (low против обычного)**: сравнивается recall и ошибка границ на эталонных моментах внутри куска. Субъективное качество описаний не оценивается.
19. **Safety settings** не реализованы: допустимые значения для Interactions API не сверены (оставлено как «сверить»). Блокировки будут обрабатываться в фазе 1 (кусок `partial`).
20. **Куки YouTube** не используются. Только публичные ссылки или локальный файл.
21. **ruff:** правило E501 отключено (длинные русские строки в отчётах), форматирование держит `ruff format`. **mypy** в режиме strict на `src` и `scripts`.
22. **CI** написан, но не запускался: у проекта нет удалённого репозитория. Те же команды проверены локально.
23. Docker Compose проверен командой `docker compose config`; контейнеры не запускались.

## Фаза 1 (CLI MVP)

24. **Хранение состояния задачи:** до введения PostgreSQL (в фазе 3) состояние активной задачи пишется в `data/jobs/{job_id}/state.json`. Это обеспечивает полную идемпотентность и автоматическое возобновление после падения с последнего завершённого этапа (S0 -> S1 -> S2 -> S3 -> S4 -> S7).
25. **Прокси 720p (S1):** создаётся через FFmpeg (`scale=-2:720`, 24 fps, CRF 30, AAC 96k, mono) в рабочей папке задачи `data/jobs/{job_id}/work/proxy_720p.mp4`. Если на вход подан локальный файл, он используется напрямую для нарезки оригиналов, а прокси — для загрузки в Gemini Files API.
26. **Слияние кандидатов (S4):** порог перекрытия — не менее 50% от длины более короткого клипа. При пересечении остаётся кандидат с высшим баллом, статус переводится в `merged`, текстовые свидетельства (`visual_evidence`, `audio_evidence`, `why_viral`, `title_options`) объединяются.
27. **Нарезка клипов (S7):** точная покадровая нарезка из оригинала через `-ss {start} -i {src} -t {dur}` с перекодированием libx264 CRF 18 и аудио-затуханиями `afade=t=in:st=0:d=0.1,afade=t=out:st={dur-0.15}:d=0.15`. Каждый готовый клип проверяется через `ffprobe` (наличие видео, аудио и соответствие длительности с допуском 0.15 с).
28. **Экспорт:** в каталог `data/out/{job_id}/` сохраняются готовые `.mp4` файлы с понятными slug-именами и общий `manifest.json`.
29. **CLI интерфейс:** `cliphunter run <target>` с поддержкой параметров `--profile`, `--budget`, `--yes` (автоподтверждение стоимости), `--min-len`, `--max-len`, `--out`. Дополнительно реализована команда `cliphunter estimate <target>`.

## Фаза 2 (Интеллект: Scan → Refine → Judge)

30. **S5 Refine окно и перевод таймкодов:** Кандидат подаётся в модель во временном окне `[start - PAD_BEFORE_S, end + PAD_AFTER_S]`, вырезанном из прокси-видео. Gemini возвращает локальные таймкоды `start` и `end` внутри этого окна. Они автоматически транслируются в глобальную шкалу секунд: `win_start + parse_ts(local_ts)`.
31. **Проверка хронометража в S5:** Если длительность после Refine выходит за пределы `[CLIP_MIN_S - tolerance, CLIP_MAX_S + tolerance]`, отправляется один повторный запрос с указанием ошибки. Если после повтора длительность всё ещё некорректна, кандидат помечается `dropped`.
32. **S5b Boundary Snapping:** Микроподгонка границ клипа осуществляется в пределах `SNAP_S` (по умолчанию 1.0 с) через анализ пауз в речи (`ffmpeg silencedetect=noise=-30dB:d=0.2`) и смен сцен (`ffmpeg select='gt(scene,0.3)'`). Если пауза найдена в окне `[boundary - SNAP_S, boundary + SNAP_S]`, граница привязывается к ней. Снэп не выбирает моменты, а предотвращает обрыв фраз стримера на полуслове.
33. **S6 Judge батчинг:** Прошедшие S5 кандидаты нарезаются в черновые mp4 и группируются пачками до 10 клипов (`min(10, settings.judge_batch)`). Пачка загружается в Gemini Files API и передаётся в одном мульти-видео запросе `client.interactions.create` с системным промптом `prompts/judge.md`. Итоговые клипы сортируются по `(score, duration_s)` по убыванию.
34. **Fallback в Judge:** Если модель вернула некорректный JSON или пропустила элемент списка, кандидаты помечаются как `accepted`, чтобы не терять материал из-за синтаксического сбоя модели.
35. **Фреймворк валидации качества (`scripts/eval.py`):** Реализован расчёт IoU (>= 0.5), Recall, Precision, F1, Mean Boundary Error до и после Refine+Snap, задержки обработки и стоимости в $/час. Поддерживает `--dry-run` на эталонных стримах (gameplay, just chatting, podcast) и формирует отчёты в `eval/reports/eval_<timestamp>.md` и `.json`.

## Фаза 3 (Сервис, API и Ревью UI)

36. **Автономность БД (SQLite по умолчанию):** По умолчанию `DATABASE_URL` выставлен в `sqlite+aiosqlite:///data/cliphunter.db` с автоматическим созданием директорий и таблиц при первом старте. Это позволяет запускать ClipHunter и проходить тесты на любой Windows/Linux машине без запущенного Docker Desktop демона. При развертывании в продакшене/контейнерах URL переопределяется через `.env` на `postgresql+asyncpg://...` без изменения кода.
37. **HTTP 206 Partial Content / Range header стриминг:** В эндпоинтах `/api/media/proxy/{id}` и `/api/media/clips/{id}` реализована потоковая отдача фрагментов с поддержкой заголовка `Range: bytes=start-end`. Это гарантирует мгновенную покадровую перемотку (scrubbing) в HTML5 `<video>` плеере веб-интерфейса без необходимости скачивать гигабайтный файл стрима целиком в память браузера.
38. **Тонкая подгонка границ (±0.1s и ±1.0s):** В интерфейсе ревью и в API (`PATCH /api/candidates/{id}`) границы `start_s` и `end_s` сохраняются с точностью до десятых долей секунды (0.1 с) и мгновенно применяются к позиции воспроизведения плеера.
39. **Шлюз ручного ревью (`awaiting_review`):** После завершения этапа S6 Judge задача переходит в статус `awaiting_review`, синхронизирует всех кандидатов в БД и ожидает действий нарезчика в UI. Если в настройках включен флаг `AUTO_RENDER=true`, шлюз пропускается автоматически.
40. **Универсальный рендер ручных и ИИ-моментов:** Моменты, добавленные пользователем вручную через интерфейс (`POST /api/jobs/{id}/candidates`), записываются как кандидаты со `status=accepted` и `source_pass=manual` и рендерятся тем же движком FFmpeg, что и моменты от ИИ.
41. **Клиентская архитектура SPA:** Веб-интерфейс реализован на чистом ванильном HTML/CSS/JS (без сторонних тяжелых фреймворков и бандлеров) с темной темой, адаптивной версткой, Google Fonts Inter/JetBrains Mono и шиной SSE событий.
42. **Запуск через CLI:** Добавлена команда `cliphunter serve` с флагами `--host`, `--port` (по умолчанию 8000) и `--reload`.

## Фаза 4 (Монтаж: Layouts, звук, шаблоны, субтитры)

43. **Архитектура фильтров монтажа (`video/layouts.py`):**
    - `original`: сохранение исходных пропорций кадра 16:9 (`null`).
    - `center_crop_9x16`: центральное кадрирование 9:16 (`crop=ih*9/16:ih,scale=1080:1920`).
    - `blur_fit_9x16`: двухслойная композиция: размытый увеличенный фон (`boxblur=30:5`) и четкий пропорциональный исходник по центру (`scale=1080:-2,overlay=(W-w)/2:(H-h)/2`).
    - `facecam_top_game_bottom_9x16`: вертикальный сплит 1080x1920: верхний блок (высота ~640px) — фейскам по нормализованным координатам профиля стримера (`facecam_rect`), нижний блок (высота ~1280px) — геймплейная зона (`gameplay_rect`), соединенные через `vstack`.
44. **Нормализация громкости и затухания звука:**
    - Для соответствия стандартам платформ коротких видео (Shorts, Reels, TikTok) применяется аудиофильтр EBU R128: `loudnorm=I=-16:TP=-1.5:LRA=11`.
    - Для исключения звуковых щелчков на стыках склейки добавляются микродаун-фейды: `afade=t=in:st=0:d=0.1` и `afade=t=out:st={dur-0.15}:d=0.15`.
45. **Шрифты и заголовочные хуки под Windows (`video/template.py`):**
    - В FFmpeg под Windows фильтр `drawtext` без явного указания `fontfile` аварийно завершается с ошибкой `Fontconfig error: Cannot load default config file: File not found`.
    - Реализовано автоопределение системного шрифта (`C:/Windows/Fonts/arial.ttf` или fallback на Linux `/usr/share/fonts/`) с обязательным экранированием двоеточия диска (`C\:/Windows/Fonts/arial.ttf`), что обеспечивает 100% надежный рендер заголовка-хука на любой ОС.
46. **Субтитры ASS Karaoke (`video/subtitles.py`):**
    - Модуль генерирует субтитры в формате Advanced SubStation Alpha (`.ass`) со стилизацией караоке (акцентное подсвечивание текущего произносимого слова) и полупрозрачной подложкой.
    - В соответствии с ТЗ модуль опционален (`SUBTITLES=false` по умолчанию), при отсутствии пакета `faster-whisper` плавно деградирует без прерывания монтажа.
47. **Сквозная интеграция параметров монтажа:**
    - Эндпоинт `POST /api/jobs/{id}/render` и фоновый воркер `render_job` принимают параметры `layout` и `template`.
    - В веб-интерфейсе ревью селектор layout передает выбранный формат в запрос рендера.
    - Манифест клипа и запись в БД `ClipORM` сохраняют фактически примененные `layout` и `template`.

## Фаза 5 (Экспорт в CapCut)

48. **Зафиксированная версия CapCut Desktop:**
    - Проверенная версия на целевой Windows-машине: **CapCut Desktop `9.6.0.4097`** (`app_id: 359289`, `app_source: "cc"`, схема черновика `version: 360000`, `new_version: "138.0.0"`).
    - Рекомендуется отключить автообновление CapCut (в настройках CapCut и/или запретом на запись папки `Apps\`), чтобы обновления клиента не ломали локальную JSON-схему черновиков.
    - Контракт схемы зафиксирован в эталонной фикстуре `tests/fixtures/capcut_9_6_0_reference.json` и проверяется smoke-тестом `test_smoke_capcut_reference_fixture` и функцией `validate_capcut_draft()`.
49. **Двойная совместимость файлов черновика (`draft_content.json` + `draft_info.json`):**
    - CapCut Desktop `9.6.0.4097` на Windows читает таймлайн из `draft_content.json`, тогда как старые сборки CapCut 5.x/6.x и сторонние утилиты (`pyCapCut` / `VectCutAPI`) обращаются к `draft_info.json`.
    - `CapCutExporter.export(clip)` синхронно записывает оба файла (`draft_content.json` и `draft_info.json`), а также `draft_meta_info.json`, `draft_agency_config.json`, `draft_biz_config.json`, `draft_virtual_store.json`, `attachment_pc_common.json`, `timeline_layout.json` и `draft_settings`.
50. **Структура таймлайна и материалов (`src/cliphunter/export/capcut.py`):**
    - Все временные интервалы в CapCut хранятся в микросекундах (`1 с = 1_000_000 мкс`).
    - На дорожку `video_main` (`type: "video"`, `render_index: 0`) помещается видеоклип с привязкой к `materials.videos`, `materials.speeds`, `materials.canvases`, `materials.sound_channel_mappings` и `materials.vocal_separations`.
    - На дорожку `title_hook` (`type: "text"`, `render_index: 15000`) помещается текстовый заголовок-хук на первые `3.5` секунды клипа (`transform.y = 0.65`, жирный белый шрифт с чёрной обводкой и полупрозрачной подложкой).
    - При наличии субтитров (`SubtitleWord` или `.ass`-файла от модуля `subtitles.py`) создаётся третья дорожка `subtitles` (`type: "text"`, `render_index: 15001`, `transform.y = -0.75`) с непересекающимися по времени фразами.
51. **Сквозная интеграция в CLI, API и Web UI:**
    - В CLI добавлен флаг `--capcut` для `cliphunter run` и отдельная команда `cliphunter capcut-export <mp4_or_dir> [--title ...] [--layout ...] [--install]`, которая умеет сразу копировать черновик в системный каталог CapCut `%LOCALAPPDATA%\CapCut\User Data\Projects\com.lveditor.draft\` и регистрировать его в `root_meta_info.json`.
    - В FastAPI добавлены эндпоинты `POST /api/clips/{clip_id}/capcut` и `GET /api/clips/{clip_id}/capcut/download` (отдаёт готовый `.zip`-архив черновика), а в Web UI на экране результатов — кнопка скачивания `🎬 CapCut (.zip)`.

## Фаза 6 (Удобства)

52. **Telegram-бот на базе `aiogram 3` (`src/cliphunter/bot/telegram.py`):**
    - Асинхронная архитектура на базе `Router`, `Dispatcher` и `Bot`.
    - Доступ защищён белым списком `TELEGRAM_ALLOWED_IDS` (при пустом списке в dev-режиме разрешён доступ для тестирования; в продакшене блокируются любые неавторизованные пользователи с выводом их `user_id`).
    - Реализована предварительная оценка стоимости перед запуском (пробинг источника, вывод названия, канала, длительности и расчёт расхода Gemini) с подтверждением через inline-кнопки `[🚀 Запустить]` и `[❌ Отмена]`.
    - Прогресс задачи стримится в Telegram через редактирование статусного сообщения с троттлингом (не чаще одного раза в 1.5 с во избежание лимитов Telegram Bot API).
    - Готовые клипы отправляются прямо видеосообщением в чат (лимит Telegram Bot API: 50 МБ). Для файлов свыше 50 МБ бот отправляет уведомление и локальный путь на сервере.

    - Запуск через CLI: `cliphunter bot [--token TOKEN]`.
53. **Запись и прогрессивный анализ идущих стримов (`src/cliphunter/ingest/live.py`, F10):**
    - Для YouTube Live, Twitch и других трансляций прямой медиа-URL (HLS/m3u8) извлекается через `yt-dlp -g`.
    - Нарезка на лету ведётся через сегментный муксер FFmpeg: `-f segment -segment_time {chunk_s} -reset_timestamps 1 chunk_%04d.mp4`.
    - Детектор завершения сегментов отслеживает появление следующего файла (когда появляется `chunk_0001.mp4`, сегмент `chunk_0000.mp4` гарантированно завершён и закрыт) или остановку FFmpeg процесса.
    - По каждому готовому сегменту создаётся пайплайн-задача `Job` (в file-mode) и запускается в фоне через `task_manager.start_job()`. Кандидаты появляются в БД, SSE-стриме и веб-интерфейсе непрерывно прямо во время стрима.
    - Запуск через CLI: `cliphunter live <url> [--chunk-s 2700] [--profile default] [--yes] [--max-chunks N]`.
54. **Поддержка Twitch и других видеоисточников (F3):**
    - В `src/cliphunter/ingest/probe.py` добавлено распознавание `twitch.tv` и `clips.twitch.tv`.
    - Для live-трансляций, где общая длительность стрима неизвестна на момент подключения (`duration is None` / `is_live=True`), пробинг не падает, а выставляет `duration_s = 0.0`.
55. **Пакетная обработка очередей ссылок (`batch`):**
    - В API добавлен эндпоинт `POST /api/jobs/batch`, принимающий массив `urls`, профиль и параметры задачи.
    - В CLI добавлена команда `cliphunter batch [targets...] [--file links.txt] [--profile ...] [--yes] [--capcut]`, поддерживающая пакетный запуск по списку ссылок из аргументов командной строки или из текстового файла.
56. **Редактор профилей в Web UI:**
    - В интерфейс добавлен модальный редактор профилей стримеров (`#modal-profiles`) с сайдбаром существующих пресетов (`default`, `evelone2004`, `gaming_action`, `just_chatting`, пользовательские) и кнопкой "+ Новый".
    - Форма позволяет интерактивно настраивать: имя, язык, игру/категорию, мин/макс длительность клипов, нормализованные координаты вебкамеры (`facecam_rect`: X, Y, W, H) и персональную промпт-надстройку для Gemini.
    - Сохранение выполняется через `PUT /api/profiles/{name}` с мгновенным обновлением списка профилей на главной странице без перезагрузки браузера.

## Фаза 7 (Полировка)

57. **Резервное копирование и восстановление БД (`src/cliphunter/maintenance/backup.py`):**
    - Для автономной SQLite БД используется нативный онлайн-бэкап `sqlite3.Connection.backup()`, гарантирующий консистентный снимок даже при активных чтениях/записях без повреждения файла.
    - Снимок автоматически сжимается через `gzip` в `data/backups/cliphunter_backup_YYYYMMDD_HHMMSS.sqlite3.gz`. Для PostgreSQL поддерживается вызов `pg_dump` со сжатием в `.sql.gz`.
    - Встроена ротация бэкапов (`keep_last=7` по умолчанию): хранятся 7 последних архивов, более старые удаляются.
    - При восстановлении (`restore_database`) проверяется целостность архива через `PRAGMA integrity_check`, а текущая БД предварительно сохраняется в `.pre_restore.bak`.
58. **Очистка устаревших данных по `RETENTION_DAYS` и ротация логов (`src/cliphunter/maintenance/cleanup.py`):**
    - `cleanup_expired_data()` удаляет файлы старше `RETENTION_DAYS` (14 дней по умолчанию) из `data/sources/`, `data/proxies/`, `data/uploads/`, `data/live/`, `data/cache/llm/` и временных рабочих папок задач `data/jobs/*/work/`.
    - **Важный инвариант сохранности:** файлы состояния задач (`state.json`) и финальные смонтированные клипы (`data/jobs/*/out/*.mp4`, черновики CapCut) никогда не удаляются автоматической очисткой.
    - `rotate_logs()` сжимает `data/logs/api_calls.jsonl` и `.log`-файлы в `.gz`-архивы при превышении порога (10 МБ по умолчанию или по флагу `--force-log-rotate`) и обнуляет активный лог-файл без разрыва дескрипторов, сохраняя последние 10 архивов.
59. **CLI и API для обслуживания:**
    - В CLI добавлены команды `cliphunter backup [--out-dir] [--keep] [--restore] [--list]` и `cliphunter cleanup [--days] [--dry-run] [--force-log-rotate]`.
    - В FastAPI добавлен системный роутер `/api/system` (`GET /api/system/storage`, `POST /api/system/backup`, `POST /api/system/cleanup`).
60. **Скрипты установки и диагностики окружения (`scripts/install.ps1`, `scripts/install.sh`, `scripts/check_env.py`):**
    - Скрипт `scripts/check_env.py` проверяет версию Python (>=3.12), наличие `ffmpeg`, `ffprobe`, аппаратного кодека `h264_nvenc`, модуля `yt-dlp`, файла `.env`, папки черновиков CapCut Desktop и по флагу `--init-db` создаёт таблицы БД и заполняет стартовые профили стримеров.
    - В `.env.example` значение `DATABASE_URL` по умолчанию синхронизировано с `config.py` (`sqlite+aiosqlite:///data/cliphunter.db`), чтобы копирование `.env.example -> .env` работало без запущенного контейнера PostgreSQL.
61. **Документация известных ограничений (`docs/LIMITATIONS.md`):**
    - Сформирован подробный перечень ограничений по квотам Gemini Interactions API, TTL файлов в Files API (~48 ч), закрытым VOD (Sub-only/Members-only), привязке схемы черновиков к CapCut Desktop `9.6.0.4097`, лимиту 50 МБ в Telegram Bot API и особенностям SQLite vs PostgreSQL.

## Импорт JSON из Google AI Studio (Бесплатный режим 0 USD)

68. **Бесплатный режим работы без платных вызовов Gemini API (`src/cliphunter/ingest/studio.py`):**
    - Для пользователей без платного ключа Gemini API или желающих сэкономить бюджет реализован импорт готовых результатов анализа из веб-интерфейса Google AI Studio.
    - Парсер `parse_studio_json` автоматически очищает Markdown-блоки ````json ... ````, поддерживает форматы `ScanResponse`, списки моментов, словари с ключами `clips`/`items`/`moments`, гибкие таймкоды (`MM:SS`, `HH:MM:SS`, секунды) и нормализует категории к единому перечню.
    - Все импортированные моменты получают статус `accepted` и источник `studio_import`.
69. **Обход этапов анализа в пайплайне и воркере:**
    - При наличии `studio_json` в параметрах задачи стоимость строго устанавливается в `0.0 USD`.
    - Пайплайн выполняет S0 Ingest (пробинг метаданных) и S1 Download/Proxy (скачивание и подготовка 720p прокси для воспроизведения), после чего сразу переходит к этапу ревью (`awaiting_review`) или прямому рендеру (`render_job` / S7 Cut). Дорогостоящие этапы вызова LLM (S2, S3, S4, S5, S6) полностью исключаются.
70. **Поддержка в CLI, API и Web UI:**
    - В CLI добавлены флаги `--json` и `--json-str` для `cliphunter run`, а также отдельная команда `cliphunter import-studio <target> <json_file_or_string>`.
    - В API добавлен эндпоинт `POST /api/jobs/parse-studio-json` для валидации вставляемого JSON на лету, а в `CreateJobRequest` поддержано поле `studio_json`.
    - В Web UI на экране 1 добавлен переключатель режима «📋 Google AI Studio (0 USD)» с текстовой областью, загрузкой `.json` файла, динамическим счетчиком распознанных моментов и скрытием полей бюджета.
